## 1. 背景与动机

### 1.1 现有根因分析工具的共同缺陷

#### 1.1.1 纯推理给出根因缺少客观评判

当前面向 Linux 内核的 LLM 根因分析（RCA）工具，无论工业界还是学术界，主流形态都是：

> 读取崩溃材料（dmesg / vmcore / 调用栈）→ 推理 → 输出根因假设和置信度。

例如阿里云的 vmcore AI 诊断（drgn 加 AI 推理）、Cloudflare 的崩溃自动分析 agent，均属此类。学术界的 KernelDiag（arXiv:2607.17722）用证据图做结构化因果推理，是纯推理路线目前的最好水平——其方法级定位 Top@1 准确率为 **33.3%**（文件级 65.9%）。这个数字说明，纯推理路线远远不够可靠。

这类方案的根本问题在于：**置信度是 LLM 对自己的主观估计，不是对结论的实验检验。**

#### 1.1.2 复现程序验证归因不彻底

有的方案除了有主观推理，也会让 LLM 通过某些复现程序验证根因假设是否正确，试图让根因假设更加可靠。然而，即便 agent 给出了复现程序并成功复现了 bug，也不能证明归因正确：**多个不同的根因，可能通过同一个复现程序复现出同一个现象。** 复现验证的是“症状可以被触发”，不是“归因正确”。一个 NULL 指针崩溃，可能源于竞争窗口 A，也可能源于缺失检查 B——两者都能让复现程序稳定崩溃，而它们的解法可能会有所不同。

### 1.2 核心思路：减少主观、增加客观

#### 1.2.1 原则1：用修复补丁验证根因

基于对已有方案的反思，kdebugent 选择将根因分析进一步定量化、提供确定性判据：

> 与其估计“根因假设有多可信”，不如对假设中的“因”直接施加干预——生成修复补丁——然后观察“果”（问题现象）是否消失。

**只有知道解法是正确的，才能确认根因分析是正确的。** 补丁让问题不再复现、且系统功能没有回归，根因才获得了实验层面的支撑。这样，结论就从“带置信度的猜测”变成了“经过实验检验的因果判断”。判断环节不再有 LLM 参与，从机制上避免了幻觉影响判断。

> [!TIP]
> 当然可以说找到解法也不代表根因正确，因为可能多个归因可以由一个解法解决。但是在这种情况下，根因究竟是否准确已经无关紧要了：我们已经找到了规避这个问题的方法了，已经从实用角度将问题解决。更详细的讨论会在 2.1 节进行。

#### 1.2.2 原则2：把判断从 LLM 手里拿走

仅有干预闭环还不够。流程中每一个“是否”的判定（是否复现、是否解决、回归是否通过），都不允许 LLM 读日志“觉得对或错”，而必须是机器可以重复执行的判据。我们把这份判定标准的执行者称为 **checker**（检查器）：它回答“观察到什么现象，才算 bug 出现”。相应地，复现程序由两部分组成——**触发器**（trigger，制造触发条件）和**检查器**（checker，判定现象是否出现）。

- **LLM 负责生成**：根因假设、触发器代码、checker 判定规格（结构化 JSON，见第 5 章）、修复补丁；
- **机器负责判定**：runner 按 checker 规格对运行结果求值，输出 PASS/FAIL 及证据。

> [!TIP]
> `checker` 这个概念的灵感来自于硬件验证方向的 UCAgent 项目（https://github.com/XS-MLVP/UCAgent）

## 2. 核心方法论

### 2.1 补丁验证的局限

补丁让问题不再复现，并不等于根因就一定正确——**补丁可能绕过真正的根因，只是让问题在表现上看不出来**。有三类典型的补丁绕过根因情况，必须靠验证协议防范：

#### 2.1.1 补丁绕过问题

一种常见的情况是：补丁只是把崩溃/出错的条件特殊处理了，但是这个出错条件本身依然没有消除。这种情况在日后编写新功能时极易重复引入相同问题。例如根因是并发竞争，补丁却只是加了一个判空保护：崩溃消失了，竞争仍然存在。那么问题来了，如何减少生成的补丁只是掩耳盗铃的情况？

1. **提示词工程**：首先，在 LLM 生成修复补丁的上下文中，我们会给出实现补丁的要求——补丁的每一处改动都必须对应根因假设所指的因果环节；改动涉及的位置超出假设声明的范围时，编排器要求 agent 给出解释并在报告中标出，供人工审查重点核对。这种提示词可以减少这种掩盖问题的补丁，但是在 AI 找不到解决问题的方向时还是可能通过掩盖问题来绕过解决问题本身，以“敷衍”完用户的目标（AI的毛病：不跟用户说失败，拼了命地只想实现成功）。
2. **判别实验**：由于提示词的约束存在逃逸的情况，我们需要一种更客观的方式评判补丁不是掩耳盗铃。我们提出了判别实验这一方案（见 2.2 阶段三）：保留我们注入的最坏时序 / 强制交错，单独撤掉补丁再跑——若此时重新命中，说明补丁确实作用在那个窗口上；若撤掉补丁仍不命中，说明是别的改动恰好把时序错开了，按掩蔽性修复处理。审查的第一原则是：补丁必须作用于因果链上的环节，而不是作用于现象。无差别的防御性补丁，除非假设本身就是“缺失检查”，否则按原则拒绝。

#### 2.1.2 问题触发存在某种隐藏条件

如果问题是偶发的/在某种条件下不触发的，那么打入补丁后问题不复现也不一定说明问题解决了。

为了消除这种不确定性，以往的项目的思路可能投射到概率上：试图证明运行多少次就可以保证99.999%的可能性补丁已经解决问题了。但是这种思路存在根本性问题：

1. **偶发问题不是概率问题**。通过多跑几次不出错来确保它正确修复相当于把问题当作满足某种随机规律的概率问题，但是偶发问题不满足随机规律，而是满足条件就触发的问题——试图用随机多次运行来“碰对”，有可能出现完全没“碰”到触发条件。你永远也**无法通过重复多次实验来证明补丁解决了问题**，也就无法证明找到了根因。
2. **偶发问题找到触发条件可以尽可能触发**。一个偶发 bug 看上去随机，但找到隐藏的触发条件（指令交错顺序、内存布局、中断到达时刻、调度顺序、分配器状态）取到特定值时**一定**能触发（虽然取到触发条件的要求可能比较苛刻）。

对于这个问题，我们提出的解法是**找到问题的隐藏条件，让它必现**（见 2.2）。与其采样分布，不如把隐藏变量钉死，让 bug 在未打补丁的内核上从偶发/特殊条件触发变成必现。一旦必现，单次运行就是合法判据，不再需要多次反复运行。

### 2.2 验证协议

验证协议试图把问题的隐藏触发条件控制到让复现不再依赖运气（不靠多次跑复现程序来确保复现）。协议分三阶段，判据只在受控条件下成立。

#### 2.2.1 阶段一：抓出隐藏条件

这个阶段的目标是让 trigger 在未打补丁的内核上**确定性触发**。内核本身提供了现成的确定化手段，trigger 应优先使用这些，而不是靠`sleep`保证竞争窗口碰到一起：

| 隐藏条件类型                      | 确定化手段                                                                                                                                                                                           |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 竞态条件                          | 线程 A 和线程 B 竞争时，用 kprobe/kretprobe 或自写模块在选定指令上挂住线程 A（`wait_for_completion`），强制线程 B 先动再放行，把潜在并发场景变成强制并发竞争；必要时在单 vCPU 单步 VM 中控制调度 |
| 资源失败路径（分配失败、IO 失败） | 故障注入（`CONFIG_FAULT_INJECTION` / `fail_function`），让指定的那次 kmalloc / IO 确定性失败，而不是等它偶尔失败                                                                                     |
| 复现时间窗太窄                    | 在精确窗口点注入 `udelay`，把纳秒级窗口撑成毫秒级并稳定命中                                                                                                                                          |
| 问题出现和出错观测点离得太远      | sanitizer 把判据从“偶发的观测点崩溃”上移到“确定性的问题出现位置”（代码违例）                                                                                                                         |

**验收标准**：阶段一的验收标准是问题复现程序上保证必现。做不到必现，说明对隐藏变量的控制还不完整、对根因的理解还没到位——此时正确的动作是回到“继续控制隐藏变量”或换假设，**而不是加大运行次数**。确实无法在软件层确定化的（硬件竞争、固件、罕见中断时序），按未能判定的归因记录下来，再回头猜测其他可能的根因。

**sanitizer 前移症状**：很多 bug 偶发，是因为“坏事发生”到“可观测崩溃”之间本身隔着运气（越界写了，但写坏的字节是否被后续用到、是否致命是偶然的）。sanitizer 把这层运气直接删掉，让判据落在确定性的违例点上：

- KASAN：非法访问发生的瞬间报告，不等被写坏的数据偶然引发 panic；
- KMSAN：未初始化内存一旦被使用就报；
- KCSAN：数据竞争发生时报告，不依赖它是否恰好导致崩溃；
- UBSAN：未定义行为点触发。

runner 默认在 sanitizer 内核上跑 checker。这一步单独就能消掉一整层偶发性，性价比最高。

#### 2.2.2 阶段二：补丁后对抗验证

真正的修复应在最坏情况下也成立，而不是在“正常时序”下看起来没事。验证打补丁的内核时，带着阶段一那套控制手段一起上：延迟注到最大、强制并发竞争、单 CPU 抢占、sanitizer 全开。

- 补丁若真关上了窗口 → 在对抗时序下依然不命中 → `PASS`；
- 补丁若只是把窗口缩小了（典型假修复）→ 对抗时序下会被重新打成 `FAIL`。

**不采样分布，而攻击极值。** 这是对“偶发不是概率问题”最直接的工程回应。

**阶段三：判别实验（兼阴性对照）。** 保留阶段二注入的最坏时序 / 强制交错，单独撤掉补丁再跑一次：

- 必须重新命中（`FAIL`）——这同时证明两件事：控制手段确实把 bug 逼成了必现（环境没漂移），以及补丁的作用点就在那个窗口上（而非别处恰好错开了时序）；
- 若撤掉补丁仍不命中，说明要么环境 / 控制手段漂移（验证作废），要么补丁是掩蔽性的（标记 `MASKING-SUSPECT`，进入人工重点审查）。

**行为类的扩展**：行为类 checker 是连续指标加阈值。确定性化对行为类意味着**固定负载与拓扑**，让受控条件下的指标行为可复现，而不是靠多次采样取分布。阈值取“理论健康值与受控 buggy 行为实测值之间”的位置：buggy baseline 在受控条件下必须稳定落在越界侧，补丁后必须稳定回到健康侧。锁定的阈值与受控条件随规格一起写进报告。

### 2.3 结论分级

报告中的根因结论必须带验证状态标签，不允许模糊表述：

- `VERIFIED`：trigger 已确定性化（buggy baseline 必现），补丁在对抗时序 + sanitizer 下稳定 PASS，判别实验通过。根因获得实验层面的因果支撑；
- `MASKING-SUSPECT`：补丁让现象消失，但靶向性检查或判别实验未通过（疑似只掩盖了现象），必须进入人工重点审查；
- `UNCONTROLLED`：无法把 bug 确定性化（隐藏变量控制不住），因而不具备下 PASS 的资格。诚实标记并升级到更强工具（syzkaller 复现最小化、hypervisor record-replay 确定性重放），而不是用一个包装过的置信度数字充数——这与“把判断从 LLM 手里拿走”同源：达不到机器可判定，就不判定；
- `HYPOTHESIS-ONLY`：复现失败或验证未完成，只是带证据链的假设排序。

### 2.4 多假设与区分性实验

根因假设节点输出的是**按优先级排序的多个假设**（每个假设含因果链、预期修复位置、可测试化建议），而不是单一假设。在动手写复现代码之前，优先做**区分性实验**：如果假设 A 成立，在条件 X 下应该出现现象 Y；如果假设 B 成立，则不应出现。这类实验成本低，却往往能直接排除一部分假设，比直接写复现代码划算。区分性实验通过沙箱微运行工具执行（见 3.4），运行在假设节点的 ReAct 循环（LLM 循环调用工具、依据结果继续推理的执行模式）内，有独立预算。

### 2.5 bisect 支路

对回归类 bug（人工输入版本区间 + git 历史可用 + 基线复现可靠），`git bisect run` 是最确定的定位手段：直接命中引入问题的 commit，修复即 revert/fixup 该 commit，之后汇入统一的补丁验证协议。编排器在满足条件时优先走 bisect 支路，假设驱动的路径作为备选（非回归 bug、或 bisect 代价过高时）。构建成本由 ccache 和浅层构建缓存控制。

## 3. 总体架构

### 3.1 分层总览

```
┌─────────────────────────────────────────────────────────────┐
│  编排层（确定性代码，无 LLM）                                  │
│  状态机（流程图实现）· 预算控制 · journal · 断点续跑 · 路由校验  │
├─────────────────────────────────────────────────────────────┤
│  节点层（LLM 子 agent，每节点独立上下文）                       │
│  假设 · 复现生成 · 补丁生成 · 报告撰写 · 行动路由提议            │
│  节点 = f(case_state) -> artifacts（纯函数式接口）             │
├─────────────────────────────────────────────────────────────┤
│  工具层                                                       │
│  drgn(+调度helper库) · crash · ripgrep · git(log -S/blame/    │
│  bisect) · objdump · pahole/BTF · 沙箱微运行                  │
├─────────────────────────────────────────────────────────────┤
│  沙箱与构建层（异步作业队列：SQLite 作业表 + worker 池）        │
│  QEMU(KVM) · ArchProfile · initramfs · 内核构建(容器+ccache)  │
│  · 调试变体构建 · 回归测试 tier0-2                            │
├─────────────────────────────────────────────────────────────┤
│  产物层                                                       │
│  cases/<id>/{inputs, hypotheses, repro, runs, patches,       │
│  report} · 全部带哈希 · 报告结论可溯源                         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 编排层

- **状态机**：流程图（第 4 节）的确定性实现。图的规模小、结构稳定（约 12 个节点），系统的复杂度都在基础设施（构建、沙箱、产物管理）而不在图本身——这是选择自研而不是引入框架的主要理由；
- **journal**：每次状态迁移追加一条 JSONL（时间戳、迁移、输入输出产物哈希、预算余量），全程可审计、可回放、可断点续跑；
- **暂停与恢复**：人类审查可能隔天进行。暂停时的状态完全持久化，之后由 CLI 唤醒继续；
- **预算系统**：全局 case 预算（case 指一次根因分析任务的完整实例；涵盖 token、墙钟时间、构建次数、QEMU 启动次数）+ 每节点独立预算（工具调用数、ReAct 迭代数）。预算耗尽走“未解决出报告”出口，不静默失败；
- **路由校验**：LLM 在限定的行动集合内提议下一步行动，编排器校验迁移合法性和预算余量后执行——LLM 提议、机器裁决。

### 3.3 节点层：上下文隔离

超长 case 的完整历史放进单一对话，会明显拉低模型质量（长上下文下注意力分散）。因此设计为：**每个流程图节点 = 一个独立上下文的 ReAct 子会话**，节点之间只通过结构化产物交接（假设 JSON、复现规格 JSON、patch、运行结果 JSON）。每个子会话拿到的是精炼后的 case 状态摘要，加上按需取用产物的工具，而不是全部历史。

### 3.4 工具层

| 工具                        | 用途                                                                                                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| drgn（+自建调度 helper 库） | vmcore 深度状态分析：cfs_rq/task_group 遍历、runqueue 状态、sched_entity 统计。helper 库为 Python，经独立 drgn worker 子进程执行（独立环境、超时/内存限制、崩溃自动重启），分析脚本崩溃不波及 agent 进程（见 3.7） |
| crash                       | 传统 vmcore 分析（bt/ps/runq/kmem/struct），批量模式                                                                                                                                                               |
| ripgrep                     | 源码检索                                                                                                                                                                                                           |
| git                         | `log -S` / `blame` / `describe` / `bisect run`（代码考古与回归定位）                                                                                                                                               |
| objdump / pahole / BTF      | 反汇编与结构布局                                                                                                                                                                                                   |
| 日志查询工具                | dmesg/console 大日志不整段放进上下文，提供 grep/分页/时间窗过滤的按需摘录                                                                                                                                          |
| 沙箱微运行                  | 假设节点内执行区分性实验（独立小预算）                                                                                                                                                                             |

工具输出一律作为数据处理、不作为指令执行，防范日志内容中夹带提示词注入（prompt injection）的风险。

### 3.5 LLM 层

- 不绑定任何模型厂商：面向 OpenAI 兼容端点做抽象（vLLM / sglang / 云厂商全覆盖），配置文件驱动；
- **按节点配置模型**（分析类节点用强模型，日志分诊类节点可用便宜模型）；
- 温度策略：分析、补丁类节点为 0；复现代码生成允许低温度（0.2），便于重试时给出不同方案；
- 一切产物用结构化输出（JSON schema 约束）。

### 3.6 沙箱与构建层

详见第 6 节。要点：异步作业队列（SQLite 作业表 + worker 池，构建、QEMU 运行、回归都是作业）、ArchProfile 架构抽象、每 case 一次基础 initramfs 加每次运行注入 payload、按输入 .config 加最小 virtio 增量构建并把 config 改动完整记入报告、可选调试变体构建（KASAN/KCSAN/lockdep）。

### 3.7 语言与框架选型

**决策：TypeScript 编排层 + Python drgn worker（子进程隔离）+ Rust 热点下沉。**

分三层，各用最合适的语言：

| 层                                                       | 语言         | 理由                                                                                                        |
| -------------------------------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------- |
| 编排/agent 层（状态机、节点、LLM 客户端、CLI/TUI、报告） | TypeScript   | LLM SDK 与结构化输出（zod）生态与 Python 等价；异步与流处理是 Node 的强项；TUI 用 OpenTUI（见下方工程纪律） |
| drgn worker（调度 helper 库）                            | Python       | drgn 及其 helpers 生态只在 Python；作为独立子进程运行，脚本崩溃不波及 agent 进程；库小而稳定，维护门槛低    |
| 性能热点（如 console 日志流式分流）                      | Rust（可选） | 经 profile 证明是热点才下沉；napi-rs 可做成 Node 原生模块，无需进程间通信                                   |

从负载特征看：本系统的工作主要是编排外部进程和处理 I/O——内核编译发生在编译器进程里，QEMU 运行发生在 QEMU 进程里，drgn 分析发生在 worker 子进程里。编排层语言的执行性能与瓶颈无关，选择依据是维护者流利度、生态与故障隔离架构。

为什么不是单语言 Python：drgn 曾被视为“必须 Python”的硬约束，但那依赖于“helper 库以 import 方式进入 agent 进程”的设计。一旦接受故障隔离——LLM 生成的分析脚本会挂起、崩溃、吃内存，本就不应与 agent 同进程——drgn 就退化为一个子进程工具，语言约束随之消失。进程隔离对 crash/QEMU/git 本来就是既定设计，drgn 沿用同一模式反而更一致。

工程纪律：

- **类型安全**：全部产物 schema 用 zod 建模（编译期 TS 类型 + 运行期校验一体）；
- **drgn worker 显式组件化**：独立 Python 环境由主程序 bootstrap（uv），版本随发布锁定；worker 崩溃自动重启并在 journal 留痕；
- **信号/响应式只用于观察层**：预算面板、作业事件、live 日志、TUI 状态订阅用响应式原语；状态机迁移本身仍是显式 FSM + journal（见 3.2）——signal 是状态转移的订阅层，不是转移本身，审计回放需要单一事实源；
- **打包**：npm/npx 分发 CLI，首次运行自动准备 drgn worker 环境；
- **TUI 层**：OpenTUI（Zig 渲染核心 + TypeScript 绑定，内置 tree-sitter 代码高亮、diff 视图与滚动容器，cell 级差分渲染无闪烁）。binding 默认 **@opentui/solid，锁定 solid-js 1.9.12**——OpenCode 的生产 TUI 用的正是这个 binding（anomalyco 同时维护两个项目，binding 不会滞留在 1.x），是经过最大规模生产验证的路径，也与维护者的 Solid 1.x 经验匹配；对应用而言精确锁定依赖版本是正常做法。Solid 2.0 的适配由 OpenTUI/OpenCode 自身需求驱动，届时随社区一起迁移，binding 薄层已隔离切换成本。@opentui/react（要求 React ≥ 19.2）与 Ink 作为回退。binding 层保持薄：UI 组件直接消费 @opentui/core 的 renderables，切换 binding 只重写胶水层。

**编排框架**：自研轻量编排层（理由见 3.2），同时借鉴 LangGraph 的三个成熟做法：节点迁移后保存状态快照、审查节点的持久化暂停、基于 journal 的历史回放。不引入 LangGraph 依赖；节点接口保持纯函数形式，将来迁移到任何框架都有退路。

## 4. 流程与节点设计

### 4.1 流程总览

![kdebugent 整体流程](assets/kdebugent-flow.svg)

编排器支持两种入口模式：

- **常规模式**：从根因假设节点开始，复现程序由 agent 生成；
- **复现已知模式**：输入自带复现程序（例如 syzkaller 报告附带的 repro），跳过复现代码生成，直接进入确定性化阶段。

两条路径在确定性化之后共用同一套验证协议。图中“是否复现”“是否解决”“回归是否通过”的判定均由机器谓词完成（见 4.3）；“选择下一步行动”与“基于人类反馈选择行动”两个路由点的精确语义见下表：

| 失败发生位置                          | 判定者       | 允许的去向                                               |
| ------------------------------------- | ------------ | -------------------------------------------------------- |
| 确定性化失败（buggy baseline 不必现） | checker 求值 | 继续控制隐藏变量 / 换根因假设 / 标 `UNCONTROLLED` 出报告 |
| 补丁验证命中 checker（未解决）        | checker 求值 | 继续控制隐藏变量 / 换根因假设 / 预算耗尽直接出报告       |
| 判别实验异常（撤补丁仍不命中）        | checker 求值 | 标 `MASKING-SUSPECT` / 换根因假设 / 换补丁               |
| 回归测试未通过                        | 测试 runner  | 重新生成补丁（同一假设）                                 |
| 人类审查反馈                          | 人           | 换假设 / 换复现 / 换补丁 / 修改后接受                    |

路由的执行方式：LLM 在限定的行动集合内提议下一步行动，编排器校验迁移合法性和预算余量后执行——LLM 提议、机器裁决（见 3.2）。

### 4.3 判定的求值主体

流程中所有“是否”的判定均由机器谓词完成，没有 LLM 参与：是否复现 = checker 在 buggy baseline 受控运行上的求值；是否解决 = 同一 checker 在补丁运行上的求值（`fail_when` 翻转）；回归是否通过 = 测试退出码加“无新增告警”的确定性检查。**“是否复现”与“是否解决”是同一条谓词的两次求值**，从机制上保证两次判定的标准不会漂移。

**三值求值，而非二值。** 一次“没命中坏现象”有两种完全不同的含义：触发条件到达了但补丁挡住了坏结果（真的解决），或者触发条件根本没到达（这次运行什么都没证明）。二值 PASS/FAIL 会把后者偷偷算成 PASS，这正是假修复的温床。因此每条 checker 除了“坏现象谓词”，还必须带一条**检查条件到达谓词**（判定“这一次确实走到了那个窗口 / 那条路径”），runner 输出三值：

- `PASS`：检查条件到达 且 坏现象未出现；
- `FAIL`：坏现象出现；
- `INCONCLUSIVE`：检查条件未到达 → 本次运行丢弃，不计入任何判定。

“没复现”永远不等于“已修复”——必须先证明检查条件确实到达，才有资格谈 PASS。在确定性化已经做到必现的前提下，正常情况每次运行的检查条件都应到达；持续出现 `INCONCLUSIVE` 本身就是信号：控制手段没钉住隐藏变量，退回阶段一继续控制，而不是接受这次“通过”。

## 5. Checker 规范

### 5.1 定义

复现程序 = 触发器 + checker，checker 的概念见 1.2.2。崩溃类 bug 的 checker 是隐式的（“崩了就算复现”），行为类 bug 的 checker 必须显式存在，否则“复现”一词没有定义。本章给出 checker 的结构化规格。

### 5.2 规格 schema（v1）

`trigger` 不再描述“循环采样多少次”，而是描述**用什么手段把隐藏变量钉死**；`checker` 除坏现象谓词外，必须带一条检查条件到达谓词（`reached_when`，对应 4.3 的三值求值）。

```json
{
  "trigger": {
    "type": "c | ebpf | kmod | sh",
    "source": "<代码或脚本>",
    "build": "static-musl",
    "control": {
      "scheme": "kprobe_block | fault_injection | udelay_inject | forced_interleave | none",
      "detail": "<例：在 __kprobe put_task_struct 入口挂起线程 A，待线程 B 跑过 free 点后放行>",
      "deterministic": true
    }
  },
  "checker": {
    "type": "console_panic | kcsan_report | kasan_report | kmsan_report | ubsan_report | lockdep_warn | ftrace_assert | metric_threshold | exit_code | watchdog_timeout",
    "spec": {},
    "fail_when": "present | absent",
    "reached_when": "<检查条件到达谓词：证明本次运行确实走到了目标窗口/路径>"
  },
  "env": {
    "arch": "x86_64 | aarch64",
    "smp": 8,
    "topology": "2 sockets × 4 cores",
    "memory_mb": 4096,
    "debug_config": "none | kcsan | kasan | kmsan | ubsan | lockdep",
    "cmdline_append": "..."
  }
}
```

`control.scheme` 对应 2.2 阶段一的确定化手段；`control.deterministic` 为真表示该 trigger 已通过 buggy baseline 必现门禁，是进入补丁验证的前提。

各 type 的 `spec` 与 `reached_when` 示例：

```json
// kasan_report：UAF，用 kprobe 强制最坏交错（坏现象上移到 KASAN 违例点）
{ "spec": { "pattern": "BUG: KASAN: use-after-free.*put_task_struct" },
  "reached_when": "kprobe:free_hit==1 && kprobe:use_hit==1",  // 释放点与使用点都走到了
  "control_ref": "forced_interleave" }

// ftrace_assert：行为类（调度），固定负载下行为可复现
{ "event": "sched:sched_migrate_task", "filter": "dest_cpu == 0",
  "window_s": 60, "max_count": 0,
  "reached_when": "some_cpu_idle_ratio > 0.8 && max_rq_depth > 10" }  // 负载确实进入了触发态

// metric_threshold：行为类（延迟），受控负载下的实测阈值
{ "metric": "wakeup_latency_p99_ms",
  "source": "ftrace:sched_wakeup→sched_switch delta",
  "op": ">", "threshold": 1.0,
  "reached_when": "sample_count >= 1000" }  // 采样量足够，指标有意义
```

`reached_when` 与坏现象谓词是两条独立的谓词：前者判定“这一次是否走到了该走的地方”，后者判定“坏结果是否出现”。两者组合出 4.3 的三值。

### 5.3 生成与判定的分离

- **LLM 生成** checker 规格（它擅长定义“什么现象算 bug”“怎样算走到了触发点”）；
- **机器求值**（checker runner）：确定性执行——console 正则流式扫描、ftrace 事件计数、kprobe 命中计数、指标聚合、超时看门狗；先对 `reached_when` 求值，未到达直接判 `INCONCLUSIVE`；
- 求值结果永远附带证据切片（命中行、事件/kprobe 计数明细、指标序列），写入产物供报告引用。

### 5.4 双重求值与阈值锁定

同一份 checker 定义在两个判定中复用：buggy baseline 受控运行要求 `fail_when: present` 命中（复现成立），补丁运行要求 `fail_when: absent`（解决成立）。两次求值都先过 `reached_when`，避免把“没走到”误当成“解决了”。行为类的阈值在 2.2 阶段三的受控条件下确定并锁定：buggy baseline 必须稳定落在越界侧、补丁后稳定回到健康侧；锁定的阈值与受控条件随规格 JSON 一起写进报告。

## 6. 沙箱与构建系统

### 6.1 QEMU 沙箱

- KVM 加速（不可用时回退 TCG，并标注性能差异）；
- **确定性设置**：固定 vCPU 拓扑（调度 bug 常依赖拓扑）、`nokaslr`、固定内存大小；拓扑按复现规格 `env` 配置（如 `-smp 8,sockets=2,cores=4`）；
- 隔离：无网络或仅受控 NAT，宿主目录只读挂载（9p/virtiofs）；agent 生成的代码以 root 运行于 guest 内，与宿主严格隔离；
- 崩溃检测：`panic=-1` + `-no-reboot`，QEMU 退出码和 console 模式双通道；
- 挂起检测：看门狗超时（默认 300s，可按复现规格覆盖）；
- 每次运行的产物：console.log（流式落盘）、guest dmesg、checker 求值结果 JSON。

### 6.2 initramfs

每 case 构建一次基础镜像，后续所有运行复用；每次运行只注入 payload：

```
initramfs-base/
  /init            # 主控脚本：解析 cmdline 中的 kdbg 运行参数
  /bin/busybox
  /usr/bin/<静态链接的 trigger>
  /checker/         # 采集器：ftrace 启停、指标采样、事件计数
  /results/        # 结果序列化 → 9p/virtio 回传宿主
payload-per-run/
  /repro.conf      # 运行 id、控制手段参数、checker 参数
```

### 6.3 内核构建管线

- **保真度原则**：以输入 .config 为基线构建补丁内核。QEMU 硬件所需的驱动（virtio、console）以**最小增量**并入，增量 diff 记录入报告（config 改动透明化）；
- 构建在容器内进行（工具链与目标内核的构建要求对齐），ccache 加速增量构建；
- 调试变体（KASAN/KCSAN/lockdep/UBSAN，UBSAN 启用 signed-integer-overflow 检测）作为可选构建，用于复现加速、race 类验证和算术溢出类问题的确定性检测；
- 产物：Image/bzImage + vmlinux（供符号与 drgn 使用），哈希入产物库。

### 6.4 回归测试分层

| tier | 内容                                             | 时间盒           | 判定                       |
| ---- | ------------------------------------------------ | ---------------- | -------------------------- |
| 0    | 启动 + 基础 syscall/用户态冒烟                   | < 2 min          | 退出码 + 无新 WARN         |
| 1    | kselftest 中 sched/cgroup/futex 相关子集         | < 15 min         | 全通过 + 无新 lockdep 报告 |
| 2    | rt-tests（cyclictest/hackbench）+ stress-ng 子集 | < 30 min（可配） | 通过 + 行为类指标不劣化    |

### 6.5 并发模型

- 编排器为 Node.js 单进程（异步 I/O）；作业（build / qemu-run / regression）入 SQLite 作业表，worker 池消费，信号量限制并发 QEMU 实例数；
- 作业带超时、重试、断点续跑（journal 和作业表双记录）；
- M2 起支持多假设并行探索（并行派生多个验证作业）。

## 7. 人机协同

- **v1 形态：CLI/TUI**（TUI 基于 OpenTUI，内置代码高亮与 diff 视图）。`kdbg case review <id>` 进入审查：浏览报告、深入查看任意产物（运行日志、checker 判定细节、patch diff、假设 JSON）、逐节批注；
- **反馈方式**：自由文本（写入 journal，回注到目标节点的上下文）+ 动作选择（换假设 / 换复现 / 换补丁 / 接受结束），去向见 4.1 的路由表；
- **审查提示置顶**：`MASKING-SUSPECT` 补丁、`UNCONTROLLED` 结论、config 偏差、确定性化所用的控制手段清单；
- 验证全部通过时，是否仍要人工复核，由使用者自行决定，工具不强制；
- 审查可跨天：暂停状态完全持久化；
- 后续视需要升级 Web 界面，CLI 协议层不变。

## 8. 报告规范

**第一原则：每条结论都必须注明出处。** 报告中每一条结论、证据和分析，都要标注具体出处——代码位置（file:line）、符号、commit 或产物路径——让开发者能从报告的任意一句话直接跳到对应代码或原始证据，方便比对、思考和讨论。

### 8.1 报告骨架

1. **摘要**：现象、根因一句话、补丁一句话、验证矩阵、结论分级标签（2.3 节）；
2. **输入清单与校验**：全部输入哈希、一致性校验结论、config 偏差记录；
3. **证据链**：观察 → 工具+命令 → 原始输出摘录 → 解释，逐条标注出处；
4. **根因分析**：因果链叙述（代码位置标注）、**被排除的替代假设及排除理由**、区分性实验结果；
5. **复现**：触发器代码、checker 规格、确定性化所用的控制手段（如何把隐藏变量钉死到必现）、构建/运行说明；
6. **补丁**：diff、每处改动与假设的对应关系、替代方案说明；
7. **验证矩阵**：buggy baseline 必现证据 × 补丁在对抗时序 + sanitizer 下的 PASS × 判别实验（撤补丁重新 FAIL）+ 回归测试结果，每格附三值求值与证据切片；
8. **局限与不确定因素**：确定性化的覆盖程度（哪些隐藏变量被钉死、哪些没控制住）、行为类阈值与受控条件的锁定依据、config 偏差的潜在影响；
9. **审计索引**：journal 引用，以及失败尝试的完整记录（走不通的假设、废弃的复现代码版本）。

### 8.2 出处校验

报告生成后，由一段确定性的校验程序逐条检查报告中的出处：file:line 必须存在于对应 commit 的源码树中；产物路径必须存在，且内容哈希一致。任何一条对不上，报告即视为不合格，重新生成（最多重试 3 次）。经过这道检查，LLM 编造的代码引用在机制上无法留在最终报告里。

## 9. 评估方案

### 9.1 基准

- **崩溃类**：KGYM 基准（KernelDiag 论文采用）抽样 15–20 例——279 个真实内核崩溃，每个 case 含崩溃报告、复现脚本、执行 trace 和 golden patch（标准修复补丁），可作标准答案；
- **行为类**：自建调度基准 10 例起步——从上游 sched git log 的 `Fixes:` 标签中选取可复现的行为类修复（负载不均、带宽控制、延迟回归），以真实的修复 commit 为标准答案。目前没有同类基准，需要先建起来。首批 case 卡片（M0 管线验证两例 + M1 分析型旗舰一例）见 `benchmarks/cases.md`，卡片格式即后续基准 case 的统一格式；
- 基准集开放贡献：任何历史 bug 都可以按统一格式沉淀为新的基准 case。

### 9.2 指标

| 指标       | 定义                                                                 |
| ---------- | -------------------------------------------------------------------- |
| 定位准确率 | 根因函数/commit 命中标准答案的比例（Top@1/Top@3）                    |
| 确定性化率 | trigger 达成 buggy baseline 必现的比例（非 `UNCONTROLLED` 的占比）   |
| 验证通过率 | 协议全部通过 / 进入验证的 case                                       |
| 假修复率   | 人工审查否决的数量，加上基准集中已知可被掩蔽补丁“修复”的案例的误判数 |
| 成本       | 每 case 墙钟时间、token、构建次数                                    |
| 人审效率   | 平均反馈轮数、审查耗时                                               |

## 11. 风险与开放问题

### 11.1 风险与对策

| 风险                                                            | 对策                                                                                                                  |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 生产 bug 无法在 QEMU 确定性化（拓扑、定时器、真实硬件特性差异） | 标 `UNCONTROLLED`、如实说明能力边界并升级到更强工具；ArchProfile 支持精细的拓扑模拟                                   |
| 掩蔽性修复通过验证                                              | 靶向补丁约束 + 判别实验（撤补丁须重新 FAIL）+ MASKING-SUSPECT 分级 + 人工审查第一原则                                 |
| 行为类 checker 阈值主观                                         | 受控条件下的阈值锁定协议（buggy 落越界侧、补丁落健康侧）+ 人工确认阈值                                                |
| 偶发 bug 看似随机、实为隐藏变量未控制                           | 确定性化优先（强制交错 / 故障注入 / udelay / sanitizer）把必现做出来，而非加大运行次数；做不到则诚实标 `UNCONTROLLED` |
| LLM 编造不存在的符号/行号                                       | 工具返回真实错误供 agent 自行纠正；报告出处校验在机制上兜底                                                           |
| 构建与 token 成本                                               | ccache、增量构建、大日志按需摘录、按节点配模型                                                                        |
| 日志内容夹带提示词注入                                          | 工具输出一律作为数据处理；沙箱无网隔离                                                                                |
| 非主线内核（发行版或定制树）与上游差异                          | 输入一致性校验以实际源码树为准；不假设与主线等价                                                                      |

### 11.2 开放问题（后续讨论）

1. 行为类基准的标准答案定义：效应量多大算 bug，边界案例如何裁决；
2. 多 case 并发时的资源调度与优先级；
3. 报告渲染：Markdown 之外是否提供带源码跳转的 HTML 视图；

## 12. 决策记录

| #   | 决策点       | 结论                                                                | 关键理由                                                                                                 |
| --- | ------------ | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| D1  | 方法论       | 干预验证闭环（补丁 → 不复现 → 无回归）                              | 复现只能证明症状可触发，不能证明归因正确；不同根因可能通过同一个复现程序                                 |
| D2  | 判定机制     | checker 机器谓词，LLM 仅生成规格                                    | 判定环节完全不经 LLM，避免幻觉影响结论                                                                   |
| D3  | 验证形态     | 确定性化（夺取隐藏变量→必现门禁）+ 对抗验证 + 判别实验 + 三值求值   | 偶发不是概率而是未控制的隐藏变量；采样提高置信度会把“恰好没触发”误判为“已修复”，应攻击极值而非采样分布   |
| D4  | MVP bug 范围 | 崩溃类 + 行为类并行（设计层面），崩溃类先行（实施层面）             | 调度类问题大量属于行为类，checker 抽象必须从第一天就兼容两类                                             |
| D5  | 架构         | 以 ArchProfile 抽象承载架构差异，首期 x86_64 与 aarch64，可扩展     | 架构差异必须显式建模，避免散落在构建与沙箱代码各处                                                       |
| D6  | 输入         | 增加内核源码树（含 git 历史）为一等输入                             | 没有源码能力减半；补丁生成、代码定位、git 考古、bisect 全依赖它                                          |
| D7  | LLM 部署     | 不绑定厂商（OpenAI 兼容端点抽象），按节点配模型                     | 不同环境可用的模型服务不同（本地推理或云服务），避免绑定单一厂商                                         |
| D8  | 审查交互     | v1 CLI/TUI                                                          | 最快落地；协议层为 Web 升级留出空间                                                                      |
| D9  | 编排         | 自研轻量状态机 + journal（借鉴 LangGraph 成熟做法，不引依赖）       | 图小而稳定；复杂度在基础设施；开源贡献者画像是内核开发者                                                 |
| D10 | 语言         | TypeScript 编排层 + Python drgn worker（子进程隔离）+ Rust 热点下沉 | drgn 经子进程隔离后不再约束编排层语言；TS 的 LLM 生态（SDK/zod）与 Python 等价；三层各自匹配负载特征     |
| D11 | bisect       | 回归类 + git 历史 + 可靠复现时优先走 bisect 支路                    | 最确定的定位手段，与干预验证思路一致                                                                     |
| D12 | 许可证       | Apache-2.0                                                          | GPL 组件（crash/QEMU 等）均为子进程调用，drgn 为 LGPL-2.1-or-later，无许可证传染；宽松许可证利于社区采用 |

## 附录 C：术语表

| 术语              | 定义                                                                                                                                                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| checker（检查器） | 对“观察到什么现象才算 bug 出现”做确定性判定的组件；复现程序 = 触发器 + checker。命名承自硬件验证的 checker，区别在于后者多停留在静态检查（语法、格式），本方案的 checker 对运行结果做动态判定；测试理论中的对应概念为 test oracle |
| 隐藏变量          | 决定偶发 bug 是否触发的不可见条件（指令交错顺序、内存布局、中断到达时刻、调度顺序、分配器状态等）；偶发不是概率，而是这些变量未被控制                                                                                             |
| 确定性化          | 用强制交错（kprobe 挂起）、故障注入、udelay 注入、sanitizer 等手段把隐藏变量钉死，使 bug 从偶发变为必现                                                                                                                           |
| 必现门禁          | 进入补丁验证的前提：trigger 必须在 buggy baseline 上确定性触发（必现）；做不到则继续控制隐藏变量或标 `UNCONTROLLED`，而不是加大运行次数                                                                                           |
| 对抗验证          | 带着最坏时序 / 强制交错 / sanitizer 全开验证补丁，攻击极值而非采样分布；假修复会在对抗时序下被重新打成 FAIL                                                                                                                       |
| 判别实验          | 保留最坏时序、单独撤掉补丁再跑：须重新 FAIL，才同时证明环境没漂移且补丁作用点就在该窗口上；撤补丁仍不命中则疑似掩蔽性修复                                                                                                         |
| 检查条件到达      | checker 的 `reached_when` 谓词，判定“本次运行确实走到了目标窗口/路径”；未到达判 `INCONCLUSIVE`，防止把“没走到”误当“已解决”                                                                                                        |
| 靶向补丁          | 每处改动都对应根因假设所指因果环节的补丁；与之相对，只让现象消失、不触及根因的称为掩蔽性修复                                                                                                                                      |
| 区分性实验        | 能区分不同假设的低成本实验：若假设 A 成立，条件 X 下应出现现象 Y                                                                                                                                                                  |
| ArchProfile       | 架构档案：QEMU machine/console/工具链前缀/config 基线等架构差异的抽象                                                                                                                                                             |
| journal           | 编排层状态迁移的只追加（append-only）JSONL 日志，支撑审计、回放和断点续跑                                                                                                                                                         |
| 出处              | 报告中每条结论标注的依据位置（代码行、符号、commit 或产物路径）                                                                                                                                                                   |

| case | 一次根因分析任务的完整实例：从输入材料到最终报告的全过程（产物目录见附录 B） |
| ReAct | LLM 的执行模式：循环调用工具、观察结果、继续推理，直至得出结论；各节点的 LLM 子会话均按此模式运行 |
