## 1. 背景与动机

### 1.1 现有根因分析工具的共同缺陷

#### 1.1.1 纯推理给出根因缺少客观评判

当前面向 Linux 内核的 LLM 根因分析（RCA）工具，无论工业界还是学术界，主流形态都是：

> 读取崩溃材料（dmesg / vmcore / 调用栈）→ 推理 → 输出根因假设和置信度。

例如阿里云的 vmcore AI 诊断（drgn 加 AI 推理）、Cloudflare 的崩溃自动分析 agent，均属此类。学术界的 KernelDiag（arXiv:2607.17722）用证据图做结构化因果推理，是纯推理路线目前的最好水平——其方法级定位 Top@1 准确率为 **33.3%**（文件级 65.9%）。这个数字说明，纯推理路线远远不够可靠。

这类方案的根本问题在于：**置信度是 LLM 对自己的主观估计，不是对结论的实验检验。**

#### 1.1.2 复现程序验证归因不彻底

有的方案除了有主观推理，也会让 LLM 通过某些复现程序验证根因假设是否正确，试图让根因假设更加可靠。然而，即便 agent 给出了复现程序并成功复现了 bug，也不能证明归因正确：**多个不同的根因，可能通过同一个复现程序复现出同一个现象。** 复现验证的是“症状可以被触发”，不是“归因正确”。一个 NULL 指针崩溃，可能源于竞争窗口 A，也可能源于缺失检查 B——两者都能让复现程序稳定崩溃，而它们的解法可能会有所不同。

### 1.2 核心思路：减少主观、增加客观

#### 1.2.1 原则1：用修复补丁验证根因

基于对已有方案的反思，kdebugent 选择将根因分析进一步定量化、提供确定性判据：

> 与其估计“根因假设有多可信”，不如对假设中的“因”直接施加干预——生成修复补丁——然后观察“果”（问题现象）是否消失。

**只有知道解法是正确的，才能确认根因分析是正确的。** 补丁让问题不再复现、且系统功能没有回归，根因才获得了实验层面的支撑。这样，结论就从“带置信度的猜测”变成了“经过实验检验的因果判断”。判断环节不再有 LLM 参与，从机制上避免了幻觉影响判断。

> [!TIP]
> 当然可以说找到解法也不代表根因正确，因为可能多个归因可以由一个解法解决。但是在这种情况下，根因究竟是否准确已经无关紧要了：我们已经找到了规避这个问题的方法了，已经从实用角度将问题解决。更详细的讨论会在 2.1 节进行。

#### 1.2.2 原则2：把判断从 LLM 手里拿走

仅有干预闭环还不够。流程中每一个“是否”的判定（基线是否复现、补丁后是否仍复现、回归是否通过），都不允许 LLM 读日志“觉得对或错”，而必须是机器可以重复执行的判据。我们把这份判定标准的执行者称为 **checker**（检查器）：它回答“观察到什么现象，才算 bug 出现”。相应地，复现程序由两部分组成——**触发器**（trigger，制造触发条件）和**检查器**（checker，判定现象是否出现）。

- **LLM 负责生成**：根因假设、触发器代码、checker 判定规格（结构化 JSON，见 4.2.4）、修复补丁；
- **机器负责判定**：runner 按 checker 规格对运行结果求值，输出 PASS/FAIL 及证据。

> [!TIP]
> `checker` 这个概念的灵感来自于硬件验证方向的 [UCAgent 项目](https://github.com/XS-MLVP/UCAgent)

## 2. 核心方法论

### 2.1 补丁验证的局限

补丁让问题不再复现，并不等于根因就一定正确——**补丁可能绕过真正的根因，只是让问题在表现上看不出来**。有两类典型的补丁绕过根因情况，必须靠验证协议防范：

#### 2.1.1 问题偶发出现

如果问题是偶发的/在某种条件下不触发的，那么打入补丁后问题不复现也不一定说明问题解决了。

为了消除这种不确定性，以往的项目的思路可能投射到概率上：试图证明运行多少次就可以保证99.999%的可能性补丁已经解决问题了。但是这种思路存在根本性问题：

1. **偶发问题不是概率问题**。通过多跑几次不出错来确保它正确修复相当于把问题当作满足某种随机规律的概率问题，但是偶发问题不满足随机规律，而是满足条件就触发的问题——试图用随机多次运行来“碰对”，有可能出现完全没“碰”到触发条件。你永远也**无法通过重复多次实验来证明补丁解决了问题**，也就无法证明找到了根因。
2. **偶发问题找到触发条件可以稳定触发**。一个偶发 bug 看上去随机，但找到隐藏的触发条件（指令交错顺序、内存布局、中断到达时刻、调度顺序、分配器状态）取到特定值时**一定**能触发（虽然取到触发条件的要求可能比较苛刻）。

对于这个问题，我们提出的解法是**找到问题的隐藏条件，让它必现**（见 2.2.2）。与其采样分布，不如把隐藏条件钉死，让 bug 在未打补丁的内核上从偶发/特殊条件触发变成必现。一旦必现，单次运行就是合法判据，不再需要多次反复运行。

#### 2.1.2 补丁绕过问题

一种常见的情况是：补丁只是把崩溃/出错的条件特殊处理了，但是这个出错条件本身依然没有消除。这种情况在日后编写新功能时极易重复引入相同问题。例如根因是并发竞争，补丁却只是加了一个判空保护：崩溃消失了，竞争仍然存在。那么问题来了，如何减少生成的补丁只是掩耳盗铃的情况？

1. **提示词工程**：首先，在 LLM 生成修复补丁的上下文中，我们会给出实现补丁的要求——补丁的每一处改动都必须对应根因假设所指的因果环节；改动涉及的位置超出假设声明的范围时，编排器要求 agent 给出解释并在报告中标出，供人工审查重点核对。这种提示词可以减少这种掩盖问题的补丁，但是在 AI 找不到解决问题的方向时还是可能通过掩盖问题来绕过解决问题本身，以“敷衍”完用户的目标（AI的毛病：不跟用户说失败，拼了命地只想实现成功）。
2. **针对性回归测试**：提示词的约束可能被逃逸，所以由独立阶段针对补丁改动范围生成回归测试，要求 buggy baseline 和 patched kernel 都 PASS。如果补丁只是绕过问题却破坏了功能，回归测试会失败；绕过问题但功能仍正常的补丁可以接受。测试没有覆盖到的改动点标为覆盖缺口，交人工审查，不能自动通过。

### 2.2 保证根因分析正确性的方法

#### 2.2.1 方法一：使用探测工具缩小根因范围

这个阶段用输入的 vmcore、vmlinux、log 以及可能自带的复现程序分析根因。

如果材料足够、或者借助drgn等调试器分析现场能定位根因，就进入下一阶段把根因确定性触发（问题本来就确定性触发的话，下一阶段不用做任何事）。

如果分析出多个可能的根因、一时排除不掉，就借助下面的手段做区分性实验，进一步缩小范围：

- `kprobe`/`kretprobe`：在怀疑的位置插桩，观察运行时的真实状态（参数、返回值、调用顺序），验证某条因果链到底走没走到；
- `CONFIG_FAULT_INJECTION`：怀疑根因在某条错误处理路径上时，主动让那次分配/IO 失败，看症状复不复现，确认这条路径是不是根因；
- 修改内核源码：当上述方案都无法准确分析出根因时，可以直接修改内核代码并运行加以验证。

#### 2.2.2 阶段二：抓出隐藏条件

这个阶段的目标是在未打补丁的内核上**确定性触发**，这种确定性触发由 checker 中的 trigger 来完成。内核本身提供了现成的确定化手段，trigger 应优先使用这些：

| 隐藏条件类型                 | 确定化手段                                                                                                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 竞态条件                     | 线程 A 和线程 B 竞争时，用 kprobe/kretprobe 或自写模块在选定指令上挂住线程 A（`wait_for_completion`），强制线程 B 先动再放行，把潜在并发场景变成强制并发竞争；必要时在单 vCPU 单步 VM 中控制调度 |
| 非常难触发的生产环境条件     | 故障注入（`CONFIG_FAULT_INJECTION` / `fail_function`），让指定的触发位置确定性失败，而不是试图在调试机器上复现生产环境才复现的问题                                                               |
| 复现时间窗太窄               | 在精确窗口点注入 `udelay`，把纳秒级窗口撑成毫秒级并稳定命中                                                                                                                                      |
| 问题出现和出错观测点离得太远 | sanitizer 把判据从“偶发的观测点崩溃”上移到“确定性的问题出现位置”（代码违例）                                                                                                                     |

**验收标准**：阶段二的验收标准是问题在复现程序上保证必现。做不到必现，说明对隐藏条件的挖掘还不完整、对根因的理解还没到位——应该回到“继续控制隐藏条件”或换假设。确实无法在软件层确定化的问题（硬件竞争、固件、罕见中断时序），按“未能判定的归因”记录下来，再回头猜测其他可能的根因。

> [!TIP]
> **sanitizer 将出错观测点前移**：很多 bug 偶发，是因为出错位置到崩溃之间隔着一段时间（越界写了，但写坏的字节是否被后续用到、是否致命是偶然的）。sanitizer 可以把时间差尽可能缩短，让检查落在确定性的违例点上：
>
> - KASAN：非法访问发生的瞬间报告，不等被写坏的数据偶然引发 panic；
> - KMSAN：未初始化内存一旦被使用就报；
> - KCSAN：数据竞争发生时报告，不依赖它是否恰好导致崩溃；
> - UBSAN：未定义行为点触发。
>
> 因此，本架构下 runner 默认在 sanitizer 内核上跑 checker。

#### 2.2.3 阶段三：回归测试

补丁让问题现象消失，可能只是绕过问题；要判断它是否破坏正常功能，靠的不是“触发点是否仍被执行”，而是针对补丁改动范围生成新的回归测试，要求 buggy baseline 和 patched kernel 都 PASS。它测的是被改功能原本就应有的正常行为。

回归测试由独立阶段的 AI 生成，输入包括根因假设、patch diff、改动涉及的函数/文件/子系统、相关源码和已有测试；补丁生成 agent 不参与。测试形态按改动位置选择：syscall/用户态接口写用户态 C 程序，驱动测 probe/bind/IO，内核内部函数用 KUnit 或测试模块，调度/内存/锁用定向 workload 加 ftrace/kprobe 指标。

硬性要求：

- **baseline 必须 PASS**：证明测试测的是原本正常的功能，而不是修复后的新行为；
- **patched 必须 PASS**：失败时先复核测试是否写错；确认后判定为回归，回到补丁生成；
- 重复运行排除 flaky；
- 测试应覆盖 patch 改动的函数/文件/分支；覆盖不到时标为覆盖缺口，交人工审查，不能自动通过。

**验收标准**：阶段三的验收标准是 patched kernel 上 `bug_detected = false`、针对性回归测试通过。绕过问题但破坏功能的补丁会在回归测试中失败；绕过问题但功能仍正常的补丁可以接受。

> [!TIP]
> 回归测试生成与补丁生成使用不同上下文，避免补丁 agent 写一个刚好绕开自己问题的测试。

### 2.3 结论分类

报告中的根因结论带验证状态标签：

- `VERIFIED`：问题被确定性复现，补丁后 `bug_detected = false`，针对性回归测试在 baseline 与 patched 上均通过。根因获得实验层面的因果支撑；
- `UNCONTROLLED`：无法把 bug 确定化（隐藏条件没找到），因而不具备进一步提修复补丁的资格；
- `HYPOTHESIS-ONLY`：复现失败或验证未完成，只是带证据链的假设排序。

### 2.4 可能的多条根因

在这个调试 agent 工具中，根因分析可能有多条结论：当问题无法被确定性复现、或者补丁验证/回归测试未通过时（即得出 `HYPOTHESIS-ONLY`、`UNCONTROLLED`，或补丁需要重做），AI 可以选择继续分析，判断其他的潜在根因。在没有得到一个 `VERIFIED` 根因的情况下，它会尝试最多 3 次。

> [!TIP]
> 当然，你也可以配置 kdebugent，让它每一次得出一个根因结论的时候就生成一份报告供工程师审阅。

## 3. 总体架构

### 3.1 分层总览

```
┌─────────────────────────────────────────────────────────────┐
│  编排层（确定性代码，无 LLM）                                  │
│  状态机（流程图实现）· 预算控制 · journal · 断点续跑 · 路由校验  │
├─────────────────────────────────────────────────────────────┤
│  节点层（LLM 子 agent，每节点独立上下文）                       │
│  假设 · 复现代码 · 复现检查条件 · 补丁生成 · 回归测试 · 报告 · 行动路由 │
│  节点 = f(case_state) -> artifacts（纯函数式接口）             │
├─────────────────────────────────────────────────────────────┤
│  工具层                                                       │
│  drgn(+调度helper库) · crash · ripgrep · git(log -S/blame/    │
│  bisect) · objdump · pahole/BTF · 沙箱微运行                  │
├─────────────────────────────────────────────────────────────┤
│  沙箱与构建层（异步作业队列：SQLite 作业表 + worker 池）        │
│  QEMU(KVM) · ArchProfile · initramfs · 内核构建(容器+ccache)  │
│  · 调试变体构建 · 针对性回归测试                          │
├─────────────────────────────────────────────────────────────┤
│  产物层                                                       │
│  cases/<id>/{inputs, hypotheses, repro, kernels, runs,        │
│  patches, tests, report} · 全部带哈希 · 报告结论可溯源         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 编排层

- **状态机**：流程图（第 4 节）的确定性实现。图的规模小、结构稳定（约 14 个节点），系统的复杂度都在基础设施（构建、沙箱、产物管理）而不在图本身——这是选择自研而不是引入框架的主要理由；
- **journal**：每次状态迁移追加一条 JSONL（时间戳、迁移、输入输出产物哈希、预算余量），全程可审计、可回放、可断点续跑；
- **暂停与恢复**：人类审查可能隔天进行。暂停时的状态完全持久化，之后由 CLI 唤醒继续；
- **预算系统**：全局 case 预算（case 指一次根因分析任务的完整实例；涵盖 token、墙钟时间、构建次数、QEMU 启动次数）+ 每节点独立预算（工具调用数、ReAct 迭代数）。预算耗尽走“未解决出报告”出口，不静默失败；
- **路由校验**：LLM 在限定的行动集合内提议下一步行动，编排器校验迁移合法性和预算余量后执行——LLM 提议、机器裁决。

### 3.3 节点层：上下文隔离

超长 case 的完整历史放进单一对话，会明显拉低模型质量（长上下文下注意力分散）。因此设计为：**共享 case_state，隔离每个节点的对话**——不是所有阶段共用一份上下文，也不是只传一份冷冰冰的 JSON。

```text
case_state --投影--> context_pack --> 当前节点 --> node_output --合并--> case_state
```

#### 3.3.1 case_state：编排层维护的唯一事实源

编排器维护一份结构化 case_state（JSON，持久化；journal 记录它的迁移）。它保存当前 case 的事实和产物引用，例如：

- 输入清单、哈希、版本与 config 校验结果；
- 当前阶段、当前假设、假设列表；
- 复现代码/trigger 的源码与构建产物引用；
- 复现规格 JSON、运行内核（vmlinux/bzImage）产物引用；
- 运行结果与 `bug_detected` 求值、针对性回归测试结果；
- patch、补丁内核、回归结果、报告草稿。

节点不直接改 case_state。节点输出 node_output，由编排器合并进 state。大对象（日志、源码、vmlinux、patch）不放进 state，只保存路径和哈希。

#### 3.3.2 context_pack：节点看到的上下文视图

每个节点启动时，编排器从 case_state 投影出 context_pack，而不是把全量 state 或完整历史塞进 prompt。典型内容包括：

- 本阶段目标与约束；
- 与当前阶段相关的 state 字段；
- 上游 handoff 解释：为什么这么做、有哪些不确定点；
- 需要读取的 artifact 引用；
- 允许的动作与预算。

节点通过工具按需读取 artifact 细节，而不是在 prompt 里携带全文。context_pack 由确定性代码组装；handoff 解释由上游节点生成，但不作为事实来源。

#### 3.3.3 handoff：结构化结果 + 解释

节点结束时返回两部分：

- **结构化字段**：本阶段结论、产物引用、下一步建议/动作；
- **解释性 handoff**：关键判断、被排除的方案、未解决问题、下游注意事项。

编排器把结构化字段合并进 case_state；解释性 handoff 进入下一节点的 context_pack。这样结构化负责“可路由、可引用”，解释负责“保留推理上下文”。

#### 3.3.4 只做最低限度的结构检查

MVP 不引入独立的语义验证层。模型可以自主探索、发现并修正内容错误；最终判据是 runner 的实验结果（`bug_detected`/针对性回归测试）。

但编排器仍需要最低限度的工程检查：JSON 能解析，编排器要读的顶层字段存在且类型正确。否则状态机无法路由。这不是对结论正确性的验证，只是让流程能跑。

一句话：**结构化保证“可传递、可路由、可回取”，不保证“正确”；正确性由模型自查和后续实验闭环承担。**

### 3.4 工具层

| 工具                        | 用途                                                                                                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| drgn（+自建调度 helper 库） | vmcore 深度状态分析：cfs_rq/task_group 遍历、runqueue 状态、sched_entity 统计。helper 库为 Python，经独立 drgn worker 子进程执行（独立环境、超时/内存限制、崩溃自动重启），分析脚本崩溃不波及 agent 进程（见 3.7） |
| crash                       | 传统 vmcore 分析（bt/ps/runq/kmem/struct），批量模式                                                                                                                                                               |
| ripgrep                     | 源码检索                                                                                                                                                                                                           |
| git                         | `log -S` / `blame` / `describe` / `bisect run`（代码考古与回归定位）                                                                                                                                               |
| objdump / pahole / BTF      | 反汇编与结构布局                                                                                                                                                                                                   |
| 日志查询工具                | dmesg/console 大日志不整段放进上下文，提供 grep/分页/时间窗过滤的按需摘录                                                                                                                                          |
| 沙箱微运行                  | 假设节点内执行区分性实验（独立小预算）                                                                                                                                                                             |

工具输出一律作为数据处理、不作为指令执行，防范日志内容中夹带提示词注入（prompt injection）的风险。

### 3.5 LLM 层

- 不绑定任何模型厂商：面向 OpenAI 兼容端点做抽象（vLLM / sglang / 云厂商全覆盖），配置文件驱动；
- **按节点配置模型**（分析类节点用强模型，日志分诊类节点可用便宜模型）；
- 温度策略：分析、补丁类节点为 0；复现代码生成允许低温度（0.2），便于重试时给出不同方案；
- 一切产物用结构化输出（JSON schema 约束）。

### 3.6 沙箱与构建层

详见第 5 节。要点：异步作业队列（SQLite 作业表 + worker 池，构建、QEMU 运行、回归都是作业）、ArchProfile 架构抽象、每 case 从源码树构建 buggy baseline 与补丁内核、每 case 一次基础 initramfs 加每次运行注入 payload、按输入 .config 加最小 virtio 增量构建并把 config 改动完整记入报告、可选调试变体构建（KASAN/KCSAN/lockdep）。

### 3.7 语言与框架选型

- **编排层、CLI、TUI：TypeScript + OpenTUI**；
- **drgn worker：Python**，独立子进程运行，脚本崩溃不波及编排进程；
- **性能热点：Rust（可选）**，只有 profile 证明需要时才使用。

产物结构用 JSON Schema 描述，CLI 通过 npm/npx 分发。

## 4. 流程与节点设计

### 4.1 整体流程

![kdebugent 整体流程](assets/kdebugent-flow.svg)

整个流程从输入材料开始：先形成根因假设，再生成问题复现代码；随后从源码树构建 buggy baseline 内核（vmlinux + bzImage），再进入“生成复现检查条件”阶段，一次性生成 trigger 和 checker 规格（checker 输出 `bug_detected`），并完成 trigger 构建（`kmod`/`ebpf` 直接使用刚构建好的内核产物）。之后由 runner 在沙箱中验证问题能否复现；复现成立后生成修复补丁并构建补丁内核，补丁让 `bug_detected = false` 后，由独立阶段生成针对性回归测试，确认功能没有被破坏，最后生成报告并交给人类审查。

流程图只有一条主路径。失败后的去向由“选择下一步行动”和“基于人类反馈选择行动”两个路由点决定；为避免图过于复杂，补丁验证与回归测试的内部分支没有画进图里，下面用文字展开。内核构建是进入沙箱前的基础设施步骤，图中未单独画出，见 4.2.3 与 5.3。

自动验证失败时，路由由 agent 在限定动作集合内提议，编排器校验迁移合法性和预算后执行；人类审查后的下一步由人的反馈驱动。

> [!TIP]
> 如果输入包含可复现的程序（例如 syzkaller 报告附带的 repro），“生成问题复现代码”这一步可以被跳过。

### 4.2 主流程逐步说明

#### 4.2.1 输入与根因假设

`vmcore`、`vmlinux`、`.config`、`dmesg` 作为输入，agent 基于崩溃现场和源码给出排序后的根因假设。这个节点回答“可能是什么问题”，后面的复现代码、检查条件和补丁都围绕它展开。

输入中的 vmlinux 主要用于现场分析（drgn/crash 的符号与 DWARF），不是沙箱里要运行的内核；运行内核必须从源码树构建。输入缺失 vmlinux 时，先由 4.2.3 的构建步骤生成用于分析的 vmlinux。

可以通过 drgn 调试器、`kprobe` 探测工具等进一步缩小根因范围（即 2.2.1 描述的方法）。

#### 4.2.2 生成问题复现代码

agent 生成候选复现代码（C/eBPF/shell），并在当前节点完成构建和静态检查（编译、语法/manifest 校验），确保代码确实能编译、能进入运行清单。构建失败就留在本节点修改代码并重试，不进入后续沙箱。输入自带复现程序时跳过生成，但仍要验证现成代码能在目标环境构建。产物是复现代码 + 构建产物 + 构建通过证明。

#### 4.2.3 构建运行内核

输入里的 vmlinux 主要用于现场分析，不是沙箱里要运行的内核；QEMU 里要跑的 buggy baseline 必须从内核源码树 + `.config` 构建出来，得到 vmlinux + bzImage。如果输入 vmlinux 缺失，也要先用源码树和 `.config` 构建出与崩溃版本匹配的 vmlinux 供分析使用。

baseline vmlinux 不只是用来启动 QEMU，也是 4.2.4 编译 trigger 的依赖：`kmod` 需要内核构建树、`Module.symvers` 和 vmlinux，`ebpf` 需要 BTF 与 `vmlinux.h`。因此 baseline 内核必须在生成复现检查条件之前完成构建，不能把未编译的 kmod/eBPF trigger 传给后续节点。

内核构建可以在根因假设和复现代码生成期间并行启动，但必须在 4.2.4 编译 trigger 前完成（最晚在进入沙箱前）：

- **buggy baseline 内核**：源码树 + 输入 `.config`（加最小 virtio/console 增量），用于 buggy baseline 复现；
- **调试变体**：按 checker 需要构建 KASAN/KCSAN/lockdep/UBSAN 变体；
- **补丁内核（后续阶段）**：生成补丁并应用后重新构建 vmlinux + bzImage，用于补丁验证和回归测试。

每次构建都通过构建作业队列执行，带 ccache 和内容哈希缓存；构建产物（vmlinux、bzImage、config 增量）进入产物库并写入报告。构建失败时回到对应节点修改源码、patch 或 config，不进入沙箱。具体构建规则见 5.3。

#### 4.2.4 生成复现检查条件

复现检查条件是将根因归因的不确定性尽可能降低的核心方法，它遵循第二章的核心方法论，生成一份结构化 JSON，描述 trigger、checker 和运行环境。规范如下：

```json
{
  "trigger": {
    "type": "c | ebpf | kmod | sh",
    "source": "<代码或脚本>",
    "entry": "/trigger/trigger",
    "build": "static-musl | kbuild | bpf-clang | none",
    "load": "exec | insmod | bpf_load",
    "control": {
      "scheme": "kprobe_block | fault_injection | udelay_inject | forced_interleave | none",
      "detail": "<例：在 put_task_struct 入口挂起线程 A，待线程 B 跑过 free 点后放行>",
      "deterministic": true
    }
  },
  "checker": {
    "type": "console_panic | kcsan_report | kasan_report | kmsan_report | ubsan_report | lockdep_warn | ftrace_assert | metric_threshold | exit_code | watchdog_timeout",
    "spec": {}
  },
  "env": {
    "arch": "x86_64 | aarch64",
    "smp": 8,
    "topology": "2 sockets × 4 cores",
    "memory_mb": 4096,
    "debug_config": "none | kcsan | kasan | kmsan | ubsan | lockdep",
    "cmdline_append": "..."
  }
}
```

规格中的两个核心部分是：

- **trigger**：使用什么触发方式、什么控制手段（强制交错、故障注入、`udelay` 注入等）能让 bug 必现，以及在哪个位置插桩（即 2.2.2 描述的抓出隐藏条件）。trigger 只用于复现，不进入回归测试；
- **checker 规格**：怎么判断坏现象确实出现，以及用什么方式观测（console panic、KASAN 报告、ftrace 断言、指标阈值等）。checker 的输出是一个布尔值 `bug_detected`。

生成阶段产出两部分：复现规格 JSON，以及按规格构建好的 trigger 产物（静态二进制 / `.ko` / eBPF `.o`）。trigger 的构建也在本阶段完成：`c`/`sh`/`kmod`/`ebpf` 按类型编译；其中 `kmod`、`ebpf` 直接使用 4.2.3 构建好的 baseline vmlinux（kbuild 树/`Module.symvers` 或 BTF/`vmlinux.h`）。编译失败就留在本节点修改 trigger 源码并重试，不把未编译的 trigger 传给后续节点。runner 后续只负责根据 JSON 和已构建产物组装 initramfs、注入 payload、启动 QEMU，不承担第一次构建。唯一例外是 `kmod` 在补丁内核上需要机械重编译：trigger 源码不变，只是目标内核 ABI 变了。

这样做的目的是让编译错误在生成节点内立刻暴露，避免“写错 → 打包 → 启动沙箱 → 才发现编译不过 → 重新走流程”的慢循环；同时生成阶段仍然不关心 initramfs 的具体布局，打包细节留给 runner。

字段说明：

- `trigger.type` 决定 trigger 的形态：`c`/`sh` 是用户态程序或脚本，`kmod` 是内核模块，`ebpf` 是 eBPF 程序；
- `trigger.entry` 是 trigger 在 guest 内的入口路径；
- `trigger.build` 与 `trigger.load` 描述构建/加载方式：生成阶段按 `build` 构建 trigger，runner 在补丁内核上按 `build` 重编译 `kmod`，并按 `load` 加载：`c` 用 `static-musl` 构建、以 `exec` 运行；`sh` 用 `none`（直接交给 busybox）、以 `exec` 运行；`kmod` 用 `kbuild` 针对目标内核构建、以 `insmod` 加载；`ebpf` 用 `bpf-clang` 编译、由 loader 以 `bpf_load` 挂载；
- `trigger.control.scheme` 对应 2.2 阶段二的确定化手段；`control.deterministic` 为真表示该 trigger 已通过 buggy baseline 必现门禁（checker 在 baseline 上输出 `bug_detected = true`），是进入补丁验证的前提；
- `checker.type` 决定 checker 的求值方式；`checker.spec` 是该类型的具体参数（例如 console 正则、ftrace 事件与过滤条件、指标名与阈值）。spec 定义“什么现象算 bug”，runner 输出 `bug_detected` 布尔值；
- `env` 固定架构、拓扑、内存和调试配置，保证 buggy baseline 与补丁运行在同一环境下比较。

各 type 的 `spec` 示例：

```json
// kasan_report：UAF，用 kprobe 强制最坏交错
{ "spec": { "pattern": "BUG: KASAN: use-after-free.*put_task_struct" },
  "control_ref": "forced_interleave" }

// ftrace_assert：行为类（调度），固定负载下行为可复现
{ "event": "sched:sched_migrate_task", "filter": "dest_cpu == 0",
  "window_s": 60, "max_count": 0 }

// metric_threshold：行为类（延迟），受控负载下的实测阈值
{ "metric": "wakeup_latency_p99_ms",
  "source": "ftrace:sched_wakeup→sched_switch delta",
  "op": ">", "threshold": 1.0 }
```

checker 在每次运行后输出 `bug_detected`：baseline 期望 `true`（坏现象出现，复现成立），补丁运行期望 `false`（坏现象消失）。回归是否通过由 2.2.3 的针对性回归测试判断，不再依赖触发点是否到达。

求值由 runner 完成：console 正则流式扫描、ftrace 事件计数、kprobe 命中计数、指标聚合、超时看门狗；结果附带证据切片（命中行、事件/kprobe 计数明细、指标序列），写入产物供报告引用。行为类的阈值在 2.2 阶段二的受控条件下确定并锁定：buggy baseline 必须稳定落在越界侧、补丁后稳定回到健康侧；锁定的阈值与受控条件随 JSON 一起写进报告。

#### 4.2.5 沙箱复现与“是否复现？”

进入图中的“沙箱环境复现问题（runner）”：runner 用 4.2.4 已构建好的 trigger/复现代码产物和复现规格 JSON、以及 4.2.3 构建好的 baseline 内核组装 initramfs、启动 guest（见 5.2），然后：

1. **先确认运行有效**：复现程序确实启动、完成或按预期终止，没有超时或环境失败。运行无效 → `INCONCLUSIVE`，本次丢弃，检查 trigger、复现代码和运行环境。
2. **再求值 `bug_detected`**。为 `true` → 复现成立，进入补丁生成；为 `false` → 问题没有复现，优先反思 trigger 是否写得正确——它可能没有制造出根因假设所需的 bug；其次检查是否遗漏其他隐藏条件、考虑更换根因假设；如果均未发现明显问题则停止后续步骤直接输出完整报告。

无法复现且在轮次耗尽后（默认 3 次）不再会执行其他路径，直接生成报告。

#### 4.2.6 生成修复补丁

复现成立后，基于根因假设生成修复补丁。要求每处改动都对应根因假设所指的因果环节；改动超出假设范围时，agent 必须解释并在报告中标出，供人工重点核对。补丁生成后应用并构建补丁内核（vmlinux + bzImage），构建失败回到补丁生成重试；补丁内核构建完成后再进入 4.2.7 的补丁验证。

对于不确定问题是否是回归问题的情况（即不确定问题是否是某个补丁的引入的 bug），agent 可以先通过对代码仓库二分查找来定位问题。

如果确定是回归类 bug，`git bisect run` 直接命中引入问题的 commit，修复即 revert/fixup 该 commit，之后汇入统一的补丁验证协议。

#### 4.2.7 沙箱补丁验证与“补丁后是否仍复现？”

补丁验证先看问题现象是否消失，再看补丁有没有破坏正常功能。进入图中的“沙箱环境补丁验证（QEMU）”后，先针对 target 内核机械重编译 `kmod` trigger（源码不变，只是目标内核 ABI 变了），其他类型直接复用已构建产物：

1. runner 在补丁内核上运行复现程序，求值 `bug_detected`。仍为 `true` → 问题没有解决，回到“生成修复补丁”或行动路由。
2. `bug_detected = false` → 问题现象消失，但不能直接接受；进入 4.2.9 的针对性回归测试。

#### 4.2.8 “补丁后是否仍复现？”

- `bug_detected = true` → 图中“补丁后是否仍复现？”为“是”，问题仍然存在，走“选择下一步行动”，可以换补丁、继续控制隐藏条件或换根因假设；
- `bug_detected = false` → “否”，问题现象消失，进入 4.2.9 的回归测试。

#### 4.2.9 针对性回归测试

补丁让问题现象消失，不代表功能仍然正常。这个阶段由**独立的 AI 测试生成节点**针对 patch 改动范围生成回归测试，补丁生成 agent 不参与，避免“自己写补丁、自己写放水测试”。

测试生成节点拿到：根因假设、patch diff、改动涉及的函数/文件/子系统、相关源码、已有测试和该功能的正常行为描述。测试形态按改动位置选择：

- syscall / 用户态接口 → 用户态 C 程序，检查返回值、副作用、`/proc`、`/sys` 状态；
- 驱动 → probe/bind/unbind、设备 IO、错误路径；
- 内核内部函数 → KUnit 或测试模块；
- 调度/内存/锁 → 定向 workload + ftrace/kprobe 指标。

判定规则：

- **baseline 必须 PASS**：证明测试测的是原本正常的功能，而不是修复后的新行为；baseline 失败说明测试写错或测的是新行为，重写测试；
- **patched 必须 PASS**：失败时先复核测试是否写错；确认后判定为回归，回到补丁生成；
- 重复运行排除 flaky；
- 测试应覆盖 patch 改动的函数/文件/分支；覆盖不到时标为覆盖缺口，交人工审查，不能自动通过；
- 如果改动子系统在 Linux 仓库里有对应的 selftest/KUnit，可选运行作为补充；没有就不额外维护测试套件；

回归测试通过后，报告记录测试代码、覆盖目标、baseline/patched 结果和覆盖缺口；有覆盖缺口时进入人工审查，不自动通过。

#### 4.2.10 报告与人类审查

生成完整报告后进入人类审查。人类可以基于报告和原始产物选择：换补丁、换复现代码、换根因假设，或结束。对应图中“基于人类反馈选择行动”的出口。

### 4.3 运行结果如何判定

每次 runner 跑完后，由 checker 对运行结果求值，不经过 LLM。结果只有三种：

- `BUG_PRESENT`：`bug_detected = true`；
- `BUG_ABSENT`：`bug_detected = false`；
- `INCONCLUSIVE`：运行无效或 checker 无法求值（未启动、超时、环境失败等），本次运行丢弃。

baseline 期望 `BUG_PRESENT`（坏现象出现，复现成立），补丁运行期望 `BUG_ABSENT`（坏现象消失）。`INCONCLUSIVE` 不是“没复现”也不是“已修复”，只说明这次运行没有产生可判断的结果；需要检查 trigger、复现代码、构建产物和运行环境。

## 5. 沙箱与构建系统

### 5.1 QEMU 沙箱

- KVM 加速（不可用时回退 TCG，并标注性能差异）；
- **确定性设置**：固定 vCPU 拓扑（调度 bug 常依赖拓扑）、`nokaslr`、固定内存大小；拓扑按复现规格 `env` 配置（如 `-smp 8,sockets=2,cores=4`）；
- 隔离：无网络或仅受控 NAT，宿主目录只读挂载（9p/virtiofs）；agent 生成的代码以 root 运行于 guest 内，与宿主严格隔离；
- 崩溃检测：`panic=-1` + `-no-reboot`，QEMU 退出码和 console 模式双通道；
- 挂起检测：看门狗超时（默认 300s，可按复现规格覆盖）；
- 每次运行的产物：console.log（流式落盘）、guest dmesg、checker 求值结果 JSON。

### 5.2 initramfs 与运行打包

每 case 构建一次基础镜像，后续所有运行复用；每次运行把 base 与 per-run payload 组装成 initramfs，trigger 和复现代码都在 payload 里。runner 的输入是 4.2.4 产出的复现规格 JSON、已构建好的 trigger/复现代码产物，以及 4.2.3 构建好的 vmlinux/bzImage（buggy baseline 或补丁内核）：它按 `env` 生成 QEMU 参数，选择对应内核启动，把 trigger、复现代码、checker 采集器和 `/repro.conf` 组装成 payload。runner 不再负责第一次构建；只有 `kmod` 在补丁内核上需要按 `trigger.build` 机械重编译。生成阶段不需要知道 initramfs 的具体布局。

```
initramfs-base/
  /init            # 主控脚本：解析参数、启动 checker、加载 trigger、运行复现代码、回收结果
  /bin/busybox
  /checker/        # 采集器：ftrace 启停、指标采样、事件计数
  /results/        # 结果序列化 → 9p/virtio 回传宿主
payload-per-run/
  /repro/repro     # 复现代码入口（C/eBPF/shell）
  /trigger/        # trigger：静态二进制 / .ko / eBPF .o + loader / sh
  /trigger/control.conf  # kprobe 挂点、故障注入、udelay 等控制参数
  /repro.conf      # 运行 id、env、trigger 类型与加载方式、checker 参数
```

guest 的 `/init` 按固定顺序编排：

1. 挂载 `/results`（9p/virtio），解析 `/repro.conf`；
2. 启动 checker 采集器（console 扫描、ftrace/kprobe 计数、指标采样）；
3. 按 `trigger.load` 加载 trigger：`exec` 启动用户态程序，`insmod` 加载内核模块，`bpf_load` 挂载 eBPF；
4. 运行复现代码，让 trigger 与复现代码共享同一组控制参数和运行环境；
5. 等待 workload 结束或看门狗超时，停止采集器，把 `checker_result.json` 写回 `/results`。

宿主侧 runner 拿到结果后，求值 `bug_detected`；回归测试由 4.2.9 的独立阶段生成和执行。`kmod` 类型的 trigger 必须针对每个目标内核（buggy baseline / 补丁内核）重新构建，不能直接跨内核复用；`ebpf` 和用户态 trigger 的复用性更好。

### 5.3 内核构建管线

沙箱里运行的内核必须由源码树构建；输入 vmlinux 只用于现场分析，不作为运行内核。

- **每个 case 至少两类内核**：buggy baseline 内核（源码树 + 输入 `.config`）和补丁内核（baseline + patch）。两类都产出 vmlinux + bzImage，后者用于补丁验证和回归测试；
- **保真度原则**：以输入 `.config` 为基线。QEMU 硬件所需的驱动（virtio、console）以**最小增量**并入，增量 diff 记录入报告（config 改动透明化）；
- **输入 vmlinux 缺失时**：用源码树 + `.config` 构建 baseline vmlinux 供 drgn/crash 分析；工具链和配置差异可能导致 build-id 与现场不一致，报告必须记录 vmlinux 来源与偏差；
- 构建在容器内进行（工具链与目标内核的构建要求对齐），ccache 加速增量构建；构建是异步作业，可在根因假设和复现代码生成期间并行启动，但进入沙箱前必须完成；
- 调试变体（KASAN/KCSAN/lockdep/UBSAN，UBSAN 启用 signed-integer-overflow 检测）作为可选构建，用于复现加速、race 类验证和算术溢出类问题的确定性检测；
- **trigger 构建**：在 4.2.4 阶段完成——`c` 用 static-musl 交叉编译，`sh` 直接使用脚本，`kmod` 使用 4.2.3 的 baseline 内核构建树执行 kbuild，`ebpf` 用 bpf-clang 编译并生成 BTF 信息；构建失败留在生成节点重试。补丁验证时 `kmod` 针对补丁内核机械重编译，构建产物随 per-run payload 注入 initramfs；
- 产物：每类内核的 Image/bzImage + vmlinux（供符号与 drgn 使用）+ config 增量，哈希入产物库。

### 5.4 回归测试

补丁让 `bug_detected = false` 后，由独立 AI 节点针对 patch 改动范围生成回归测试，补丁生成 agent 不参与。测试要求 buggy baseline 和 patched kernel 都 PASS：baseline 失败说明测试无效或测的是新行为；patched 失败说明补丁引入了回归。

测试没有覆盖 patch 改动点时标为覆盖缺口，交人工审查，不能自动通过。测试生成、执行判定、可选的内核 selftest/KUnit 和覆盖缺口处理见 `AGENTS.md`。

### 5.5 并发模型

- 编排器为 Node.js 单进程（异步 I/O）；作业（build / qemu-run / regression）入 SQLite 作业表，worker 池消费，信号量限制并发 QEMU 实例数；
- 作业带超时、重试、断点续跑（journal 和作业表双记录）。

## 7. 风险与开放问题

### 7.1 风险与对策

| 风险                                                            | 对策                                                                                                                  |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 生产 bug 无法在 QEMU 确定性化（拓扑、定时器、真实硬件特性差异） | 标 `UNCONTROLLED`、如实说明能力边界并升级到更强工具；ArchProfile 支持精细的拓扑模拟                                   |
| 绕过式修复破坏功能                                              | 针对性回归测试（baseline 与 patched 均须 PASS）+ 改动覆盖检查 + 覆盖缺口人工审查 + 可选的内核自带 selftest/KUnit      |
| 行为类 checker 阈值主观                                         | 受控条件下的阈值锁定协议（buggy 落越界侧、补丁落健康侧）+ 人工确认阈值                                                |
| 偶发 bug 看似随机、实为隐藏条件未控制                           | 确定性化优先（强制交错 / 故障注入 / udelay / sanitizer）把必现做出来，而非加大运行次数；做不到则诚实标 `UNCONTROLLED` |
| LLM 编造不存在的符号/行号                                       | 工具返回真实错误供 agent 自行纠正；报告出处校验在机制上兜底                                                           |
| 构建与 token 成本                                               | ccache、增量构建、大日志按需摘录、按节点配模型                                                                        |
| 日志内容夹带提示词注入                                          | 工具输出一律作为数据处理；沙箱无网隔离                                                                                |
| 非主线内核（发行版或定制树）与上游差异                          | 输入一致性校验以实际源码树为准；不假设与主线等价                                                                      |

### 7.2 开放问题（后续讨论）

1. 行为类基准的标准答案定义：效应量多大算 bug，边界案例如何裁决；
2. 多 case 并发时的资源调度与优先级；
3. 报告渲染：Markdown 之外是否提供带源码跳转的 HTML 视图；
4. 是否直接产出邮件格式 patch（`git format-patch` 风格）供 maintainer 流程使用；
5. 线上系统（无 vmcore，只有 dmesg 和现象描述）输入的支持路径；
6. 调试变体构建（KCSAN 等）与输入 .config 冲突时的合并策略。

| #   | 决策点       | 结论                                                                    | 关键理由                                                                                                 |
| --- | ------------ | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| D1  | 方法论       | 干预验证闭环（补丁 → 不复现 → 无回归）                                  | 复现只能证明症状可触发，不能证明归因正确；不同根因可能通过同一个复现程序                                 |
| D2  | 判定机制     | checker 机器谓词，LLM 仅生成规格                                        | 判定环节完全不经 LLM，避免幻觉影响结论                                                                   |

| D4  | MVP bug 范围 | 崩溃类 + 行为类并行（设计层面），崩溃类先行（实施层面）                 | 调度类问题大量属于行为类，checker 抽象必须从第一天就兼容两类                                             |
| D5  | 架构         | 以 ArchProfile 抽象承载架构差异，首期 x86_64 与 aarch64，可扩展         | 架构差异必须显式建模，避免散落在构建与沙箱代码各处                                                       |
| D6  | 输入         | 增加内核源码树（含 git 历史）为一等输入                                 | 没有源码能力减半；补丁生成、代码定位、git 考古、bisect 全依赖它                                          |
| D7  | LLM 部署     | 不绑定厂商（OpenAI 兼容端点抽象），按节点配模型                         | 不同环境可用的模型服务不同（本地推理或云服务），避免绑定单一厂商                                         |
| D8  | 审查交互     | v1 CLI/TUI                                                              | 最快落地；协议层为 Web 升级留出空间                                                                      |
| D9  | 编排         | 自研轻量状态机 + journal（借鉴 LangGraph 成熟做法，不引依赖）           | 图小而稳定；复杂度在基础设施；开源贡献者画像是内核开发者                                                 |
| D10 | 语言         | TypeScript 编排层 + Python drgn worker（子进程隔离）+ Rust 热点下沉     | drgn 经子进程隔离后不再约束编排层语言；TS 的 LLM 生态（SDK/zod）与 Python 等价；三层各自匹配负载特征     |
| D11 | bisect       | 回归类 + git 历史 + 可靠复现时优先走 bisect 支路                        | 最确定的定位手段，与干预验证思路一致                                                                     |
| D12 | 许可证       | Apache-2.0                                                              | GPL 组件（crash/QEMU 等）均为子进程调用，drgn 为 LGPL-2.1-or-later，无许可证传染；宽松许可证利于社区采用 |

| 输入            | 必需   | 校验内容                                                                                                                                                                                                                  |
| --------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| vmlinux         | 可选   | 存在时：ELF 架构探测（决定 ArchProfile）、build-id、DWARF 存在性、IKCONFIG 内嵌 config 提取（scripts/extract-ikconfig）、UTS_RELEASE；缺失时由源码树 + `.config` 构建用于分析的 vmlinux，并记录 build-id 可能与现场不一致 |
| vmcore          | ✓\*    | 与 vmlinux build-id 或源码版本匹配；架构匹配；可解析性（makedumpfile/ELF 头）；build-id 不一致时以源码版本为准并记录                                                                                                      |
| .config         | ✓      | 若 vmlinux 存在则与其 IKCONFIG 比对（不一致时以实际为准并记录）；vmlinux 缺失时作为构建基线                                                                                                                               |
| dmesg           | ✓      | 时间戳连续性、panic 签名存在性、与 vmcore 时间窗相容性                                                                                                                                                                    |
| 内核源码树      | ✓      | `git describe` 与 vmlinux/崩溃日志版本匹配；DWARF DW_AT_comp_dir 源路径比对；未提交改动告警；vmlinux 缺失时以源码树版本为准                                                                                               |
| 现成复现程序    | 可选   | 类型识别（syzkaller repro / C / 脚本）；需能在沙箱内构建运行；存在时跳过复现代码生成，直接进入复现检查条件生成                                                                                                            |
| 模块 .ko        | 涉及时 | build-id 与 vmcore 中模块段匹配                                                                                                                                                                                           |
| 工具链/构建容器 | ✓      | 与源码树构建要求一致                                                                                                                                                                                                      |

\*行为类问题可能没有 vmcore（线上直接采集），v1 以 kdump 产生的 vmcore 为主路径。

vmlinux 缺失不等于输入失败：可以用源码树 + `.config` 构建出分析用的 vmlinux。但无论输入 vmlinux 是否存在，沙箱里运行的内核都必须由源码树构建（见 4.2.3 与 5.3），输入 vmlinux 不会被直接启动。

任何校验失败 → 停止并生成输入诊断报告（不进入假设节点），避免输入错配被静默忽略。

## 附录 C：术语表

| 术语              | 定义                                                                                                                                                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| checker（检查器） | 对“观察到什么现象才算 bug 出现”做确定性判定的组件；复现程序 = 触发器 + checker。命名承自硬件验证的 checker，区别在于后者多停留在静态检查（语法、格式），本方案的 checker 对运行结果做动态判定；测试理论中的对应概念为 test oracle |
| trigger（触发器） | 制造触发条件的组件（用户态程序 / 内核模块 / eBPF / 脚本），可包含强制交错、故障注入、udelay 等控制手段；构建后与复现代码一起打入 initramfs 的 per-run payload，由 `/init` 加载并与复现代码协同运行                                |
| 隐藏条件          | 决定偶发 bug 是否触发的不可见条件（指令交错顺序、内存布局、中断到达时刻、调度顺序、分配器状态等）；偶发不是概率，而是这些变量未被控制                                                                                             |
| 确定性化          | 用强制交错（kprobe 挂起）、故障注入、udelay 注入、sanitizer 等手段把隐藏条件钉死，使 bug 从偶发变为必现                                                                                                                           |
| 必现门禁          | 进入补丁验证的前提：trigger 必须在 buggy baseline 上让 `bug_detected = true`；做不到则修改 trigger、继续控制隐藏条件或标 `UNCONTROLLED`，而不是加大运行次数                                                                       |
| 对抗验证          | 带着最坏时序 / 强制交错 / sanitizer 全开验证补丁，攻击极值而非采样分布；假修复会在对抗时序下被重新打成 FAIL                                                                                                                       |
| 判别实验          | 保留最坏时序、单独撤掉补丁再跑，要求 `bug_detected` 重新为 `true`，证明环境没漂移且补丁确实作用在该问题上；可选，不替代回归测试                                                                                                   |
| 复现检查条件      | trigger 的触发与控制参数、checker 规格与 env 的统称；checker 输出 `bug_detected`；在同一“复现检查条件生成”阶段一次性产出                                                                                                          |
| 针对性回归测试    | 由独立 AI 节点针对 patch 改动范围生成的测试；要求 buggy baseline 与 patched kernel 都 PASS；用于发现绕过问题但破坏功能的补丁                                                                                                      |
| 覆盖缺口          | 回归测试没有覆盖 patch 改动的函数/文件/分支，或该功能无法构造稳定测试；不能自动判通过，必须交人工审查                                                                                                                             |
| 靶向补丁          | 每处改动都对应根因假设所指因果环节的补丁；与之相对，只让现象消失、不触及根因的称为绕过式修复                                                                                                                                      |
| 区分性实验        | 能区分不同假设的低成本实验：若假设 A 成立，条件 X 下应出现现象 Y                                                                                                                                                                  |
| ArchProfile       | 架构档案：QEMU machine/console/工具链前缀/config 基线等架构差异的抽象                                                                                                                                                             |
| journal           | 编排层状态迁移的只追加（append-only）JSONL 日志，支撑审计、回放和断点续跑                                                                                                                                                         |
| 出处              | 报告中每条结论标注的依据位置（代码行、符号、commit 或产物路径）                                                                                                                                                                   |

| case | 一次根因分析任务的完整实例：从输入材料到最终报告的全过程（产物目录见附录 B） |
| ReAct | LLM 的执行模式：循环调用工具、观察结果、继续推理，直至得出结论；各节点的 LLM 子会话均按此模式运行 |
